# Kugawana — System Audit & Remediation Plan

**Date:** 2026-08-12
**Triggered by:** four field-reported problems (forgot password, food image browsing, comment box on Android, wallet points without payment).
**Method:** four parallel deep-dive investigations across the Laravel backend, the admin console, and the Expo/React Native app, cross-checked by hand against current code. Builds on `SECURITY_AUDIT.md` (2026-08-05).

---

## Headline

The wallet problem is the serious one and it is a **money leak, not just a bug**: **Pesapal is running in SANDBOX on production.** Every "payment" is fake test money, and the code then credits *real* points on it. That alone explains someone getting 2500 points with no money received — and it would look completely legitimate in the console (status `approved`, method `pesapal`). There is also a second, independent way to mint points: the console "Approve" button credits a pending top-up with **no re-check against the gateway**.

The other three are real but contained: forgot-password on the app **was never built** (the button is a "coming soon" toast), food images upload fine but the app only ever shows image #1, and the comment box is hidden behind the Android navigation bar because the screen doesn't apply the bottom safe-area inset.

---

## 1. Wallet / points — money integrity (CRITICAL)

### 1a. Pesapal is in SANDBOX in production — real points for fake payments  🔴 CRITICAL
- `.env.production:91` → `PESAPAL_BASE_URL=https://cybqa.pesapal.com/pesapalv3` (the sandbox host), with a comment that it was "kept in SANDBOX per your call."
- `config/services.php:60` defaults to the sandbox host too; the `payment_settings.pesapal_environment` column defaults to `'sandbox'` and only switches to `pay.pesapal.com` if an admin explicitly picks "Live" in the console **and** DB credentials are filled (`PaymentSetting::pesapalBaseUrl()`).
- Flow: user "pays" on `cybqa.pesapal.com` with test cards → sandbox returns `Completed` → `topupStatus`/`pesapalIpn` verify it correctly server-to-server → real points credited. **No code asserts the environment is `live` before crediting.**
- **This is the most probable cause of the 2500-point incident.**

### 1b. Console "Approve" credits points with no gateway re-check  🔴 CRITICAL
- `resources/views/console/wallet/index.blade.php:70-73` shows Approve/Reject for **any** pending top-up regardless of `payment_method`.
- `Console/WalletController.php:48-59` → `WalletService::applyTopup()` (`WalletService.php:17-35`) flips to Approved and credits — it **never calls Pesapal**.
- A user starts a Pesapal purchase and closes the WebView (or the app's ~7.5s status poll times out); the row sits `pending` forever with no reaper. An admin later sees "2500 points / Pesapal / Pending" and clicks Approve. Points issued, no payment.

### 1c. `manual` top-up path with self-invented reference  🟠 HIGH
- `Api/WalletController.php:57-90` accepts `payment_method: 'manual'` with a free-text `payment_reference`, files it pending, pings admins. The console table doesn't even display the reference — the admin approves on a name and an amount. The app never sends `manual`, so this is a raw-API path, but combined with 1b it's the same one-click outcome.

### 1d. Verification discards amount/currency/status  🟠 HIGH
- `PesapalService::transactionStatus():129-146` keeps only `payment_status_description` and throws away `amount`, `currency`, `status_code`, `confirmation_code`. So: an underpayment marked Completed still yields full points; `merchant_reference` is never cross-checked against the top-up; `REVERSED` (chargeback) is unhandled and keeps its points forever.

### 1e. Supporting gaps
- **Packages can be priced at 0** (`Console/PackageController.php:73`, `min:0`) — a mis-saved bundle mints free points.
- **Env/credential mixing** — the "Live" dropdown can be set while traffic still goes to sandbox if DB credentials aren't filled (`PesapalService::baseUrl()`).
- **Reward double-award** — `RewardService.php:32-36` does `exists()` then `credit()` unlocked, no unique index on `wallet_transactions(user_id, reference)` (also `SECURITY_AUDIT.md` L4).
- **No throttle** on `/wallet/topup` or `/wallet/topup/{id}/status`.

> **To confirm the actual 2500-point row:** `select payment_method, status, approved_by, approved_at, order_tracking_id, amount from wallet_topups where points = 2500`. `approved_by` set → 1b/1c (admin click). `approved_by` null + `order_tracking_id` set → 1a (sandbox). No topup row at all → check `wallet_transactions.reason` for `reward:…` (1e) or an admin grant. *(MySQL wasn't reachable during the audit; this query pins it down.)*

## 2. Forgot password — the app feature doesn't exist  🟠 HIGH

- App login screen `KugawanaApp/src/app/(auth)/login.tsx:157` — the "Forgot Password?" tap only fires a toast: *"Password reset is coming soon. Contact support if you are locked out."* (`en.json:481`).
- There is **no** `forgot-password` screen, **no** `auth.service` method, and **no** `/api/auth/forgot-password` route. Nothing to fix — it has to be built.
- The **console** (admin web) reset *is* implemented (`routes/web.php:64-65`, `Console/PasswordResetController.php`) using Laravel's stock broker, but it silently no-ops when SMTP is unconfigured: if `mail_settings.smtp_host` is blank, `MailConfig::apply()` leaves the `log` mailer active, the broker returns success, and the email is written to `storage/logs/laravel.log` instead of being sent — the admin sees "reset link sent" with zero delivery. From-address also falls back to `hello@example.com` (rejected/spam-binned by most providers) when unset.
- Related open item: the reset link is built from the untrusted `Host` header (`SECURITY_AUDIT.md` H0, still open) — both a security issue and a "link points at the wrong host" delivery issue.

## 3. Food images not browsable — display-only gap  🟡 MEDIUM

- **Backend is fine.** Up to 5 images are picked (multi-select already works, `PhotoPicker.tsx`), uploaded, stored as a JSON array (`FoodDonation` `images` cast), and returned as a full URL array by `FoodResource.php:43`.
- **The app throws all but the first away.** Every consumer indexes `images[0]`. The two detail screens where a user expects to browse render exactly one static image:
  - `KugawanaApp/src/app/food/[id].tsx:84-90` (buyer detail — the primary gap)
  - `KugawanaApp/src/app/food/shared/[id].tsx:83-89` (donor's own listing)
- **A reusable swiper already exists** — `KugawanaApp/src/components/ui/PagedSlider.tsx` is a horizontal, paging `FlatList` with a dot indicator, already used on the home screen. Drop it into both detail screens over `food.images` (`perSlide=1`), keep the letter-placeholder branch for zero images. No new dependency needed.
- Secondary: editing a listing from the app **replaces the whole gallery** with newly picked files (`Api/FoodController.php:104-110`) — you can't add or remove a single photo; per-image removal exists only in the web console.

## 4. Comment box hidden behind Android nav bar  🟡 MEDIUM

- Screen: `KugawanaApp/src/app/community/[id].tsx`. Root is `SafeAreaView edges={['top']}` (`:192`) — **bottom edge deliberately excluded** — and the composer (`:286`) is the last flow child with only 8px bottom padding.
- With Expo SDK 57 edge-to-edge (`edgeToEdgeEnabled=true`, transparent nav bar), the window extends *under* the ~48dp Android 3-button nav bar. The bottom inset is never applied, so the nav bar sits on top of the input and swallows the taps — exactly the Samsung report.
- **Root cause:** the screen never reads `useSafeAreaInsets()`. The correct pattern already exists elsewhere in the app — e.g. `food/shared/[id].tsx:182` uses `paddingBottom: Math.max(insets.bottom, spacing.sm)`. Also `behavior="padding"` is applied on Android unconditionally (`:205`), which double-compensates under `adjustResize`; should be iOS-only.
- **Same bug on 7 more screens** with a fixed bottom bar and no bottom inset: `community/create.tsx`, `food/create.tsx`, `food/edit/[id].tsx`, `orders/edit/[id].tsx`, `orders/rate/[id].tsx`, `profile/edit.tsx`, `profile/report.tsx`. Worth one consistent fix (a shared footer wrapper or a `useBottomInset` hook) rather than eight one-offs.

## Remediation plan (recommended order)

### Phase 0 — Stop the money leak (today)
1. **Decide go-live on Pesapal.** If you're taking real payments: set `PESAPAL_BASE_URL=https://pay.pesapal.com/v3`, set `pesapal_environment=live` in the console, fill live DB credentials, and re-test one real transaction end to end. If you're *not* live yet: **disable point purchases in the app** until you are, so no one can mint sandbox points.
2. **Guard the credit path:** in `applyTopup`/`topupStatus`, refuse to credit unless `environment === 'live'` (in production) — a belt-and-braces assertion so a stray sandbox config can never credit real points again.
3. **Fix the console Approve button:** for `payment_method = pesapal`, re-query Pesapal and only approve on a verified `Completed`; show `payment_reference` in the table for `manual`; add a stale-pending reaper.

### Phase 1 — Wallet hardening (this week)
4. Cross-check `merchant_reference` and the settled `amount` against the top-up before crediting; handle `REVERSED`.
5. Add the unique index on `wallet_transactions(user_id, reference)` and wrap reward award in a transaction (kills double-award).
6. Enforce package `price >= 1`; add throttle to the wallet routes.

### Phase 2 — Forgot password (this week)
7. Build the app flow: decide OTP-vs-link, add `POST /api/auth/forgot-password` + confirm endpoint, `Api/AuthController` methods, `auth.service` calls, and the two screens.
8. Make the mailer fail loud: if no SMTP host is configured in a non-local env, log a warning (or fail the request) instead of quietly using the `log` mailer; set a real `from_address`; log which branch `PasswordResetController::email()` took so it's diagnosable.
9. Add `trustHosts()` / `URL::forceRootUrl(config('app.url'))` (also closes `SECURITY_AUDIT.md` H0).

### Phase 3 — App UX (this week)
10. Swap the single image for `PagedSlider` on `food/[id].tsx` and `food/shared/[id].tsx`.
11. Apply the bottom safe-area inset on `community/[id].tsx` and the 7 other bottom-bar screens (shared wrapper/hook); make `KeyboardAvoidingView behavior` iOS-only.

### Phase 4 — Close remaining SECURITY_AUDIT items
12. The still-open items from 2026-08-05: H0 (host header, covered by #9), M5 (article HTML sanitization), M9 (global-content permissions), and the deployment-hardening set (secure cookie, security headers, `.htaccess`, `APP_DEBUG=false`).

## What's confirmed safe (don't waste time here)
The Pesapal IPN/callback is **not forgeable** (server re-queries by our own stored tracking id; a fabricated one matches nothing), the client WebView redirect credits nothing, order placement/refunds are race-safe after the 2026-08-05 fixes, and the top-up amount is set server-side from the package (the client can't set the price). The *only* reason unpaid points exist is the sandbox environment (1a) and the unverified admin approve (1b) — not a forgeable API.
